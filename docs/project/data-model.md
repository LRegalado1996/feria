# Data model

First draft. Each table is finalized in the ticket that creates it. Template rules apply: no JSON columns, 3NF, singular snake_case tables, camelCase columns, integer identity ids, timestamps with time zone, every foreign key states `onDelete` and has an index, and a row reached from an unauthenticated URL carries a random `token`.

**One store ([FER-038](../tickets/FER-038-single-store.md), decided 2026-11-16):** `store` holds exactly one row, which the database enforces and the migrations create; every other table keeps its `storeId`. The code no longer reads `store`'s `slug`, `isDefault`, `isActive`, `logoUrl` and five colors, `store_member`, or `user.role`'s two values; [FER-041](../tickets/FER-041-drop-unread-schema.md) drops the columns and the table, and makes `admin` the role's one value, once no deployed build reads them.

`locale` is an enum: `es`, `en`. Every table has `createdAt` and `updatedAt` unless noted.

## Pages and sections

What the storefront's pages show ([FER-020](../tickets/FER-020-home-curation.md), migration `0018`; made page-generic by [FER-058](../tickets/FER-058-pages-built-from-sections.md), migrations `0020` to `0022`). **The rule:** whatever says _where_ something appears is keyed by a page (`page_section`, `page_cover_banner`); the content itself is not (`banner`, the curated lists, the categories), so one banner or list can show on several pages. The store points at the page `/` shows (`store.homePageId`). The days (`startsOn`, `endsOn`) are `date` columns, both included, read against the business day in `America/Montevideo`; either may be empty, and the last never comes before the first (a check). The public read is `getPageContent` (`src/server/services/page.ts`), cached as `readPageContent(store, pageId, locale)`; the home is its first caller.

**Adding a block** (a new kind of section; FER-059's spotlight, migration `0023`, is the worked example): one kind in `PAGE_SECTION_KINDS` (`src/lib/schemas/page`), the CHECK `page_section_kind` regenerates with it; its content table (store-level, with its translation table when it has words); a nullable target column on `page_section` with its foreign key (cascading), its index, a CHECK `(kind = '<kind>') = (<target> IS NOT NULL)` and a unique (`pageId`, `<target>`); its variant in `pageSectionSchema` and `PageContentSection`, filled by `getPageContent` and `previewPageContent` (already filtered: a block with nothing to show is left out); and one renderer in `molecules/store-page-sections`, which the storefront and the admin's preview share. No enum changes, so no migration trap. A block whose words are the interface's needs none of the tables: "how to buy" ([FER-076](../tickets/FER-076-how-to-buy-block.md), migration `0028`) is one kind, listed in `UNTARGETED_SECTION_KINDS` so a page holds it once, its copy in `src/content/{es,en}/storefront.ts` and its renderer (`molecules/store-how-to-buy`); it is never filled in, the home included: the admin adds it with "Agregar bloque" and it goes first, right under the cover.

**Adding a page** (FER-060) needs no code: the admin's "Páginas" (`/admin/pages`) creates one (`page.create`: names, address, texts for search engines, draft or published, header), its editor (`/admin/pages/<id>`) gives it a cover, banners, spotlights and rows ("Agregar bloque"; only the home fills in every category's row, FER-020's rule) and `page.setHome` makes it the home. The storefront serves it at `/<slug>` through the one-segment route, before the catalog (`(store)/store-page-view.tsx`). **The empty case:** a database always has a home, since `0021` gives every store a page and `0022` makes the column required; a fresh database runs them right after the store is created, and `0025` gives that page its address and name.
