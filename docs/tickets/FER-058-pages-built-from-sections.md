# FER-058 Pages built from sections: the home becomes the first

- **Milestone:** M4 Storefront and orders
- **Priority:** P0
- **Status:** done
- **Depends on:** FER-020, FER-022

## Goal

What the home is built from serves any page the store makes later: a page is an ordered list of blocks (a category's row, the best sellers, the featured articles, a banner, and the blocks to come) under an optional cover of banners, and the home is simply the page the store shows at `/`.

Asked by Lucas on 2026-11-19, while deciding the home's article spotlight (FER-059): "what we are building for the home should serve to create other pages with different approaches in the future; think of all of it as reusable for more pages". The same day he added that the home is not a fixed special page: any page can be chosen as the home, and there is always exactly one.

## Scope

The foundation only, with the storefront unchanged: the data model, the services, the cached read, the content type and the renderer made page-generic, the home their first user. Creating pages, their addresses and choosing the home are [FER-060](FER-060-pages-from-the-admin.md).

## Decisions

- **Where something appears is keyed by a page; the content is not** (2026-11-19). `page_section` (a page's blocks in order) and `page_cover_banner` (the banners a page opens on, in order) are the page's; `banner`, `ranking_entry`, `featured_product` and the categories stay store-level content that sections point at, so one banner or one list can show on several pages.
- **The cover is page-scoped**, in a table of its own (`page_cover_banner`), not a section kind and not FER-020's `placement`/`coverPosition` flags on the banner: those said "in the home's cover", which a second page could not share, while a row per page and banner says it for any page with the same uniqueness rules as the sequence. A banner is in a page's cover or between its rows, never both; the service moves it from one to the other.
- **Exactly one home, held by the database** (Lucas, 2026-11-19): `store.homePageId`, required, and the pair (`store.id`, `homePageId`) references the page's (`storeId`, `id`), so it can be neither zero nor two, is always one of the store's own pages, and the database refuses to delete the page that is the home (`no action`). Chosen over a flag on the page with a partial unique index, which allows zero. Bootstrapped by migration `0021`, which gives every store with no home a page and points it there; `0022` then makes the column required. A fresh database runs the same migrations right after the one that creates the store, so it is never without a home. The column is added nullable first (`0020`) because `store` already has its row; nothing the previous build runs inserts a store.
- **`kind` is text held by a CHECK, not an enum.** A new block is then one rewritten CHECK in one migration; a new enum value could not be used in the transaction that adds it (`docs/agents/database.md` § Migrations), and every block's target CHECK would hit that. Each target column has a CHECK of its own (`(kind = 'banner') = (bannerId IS NOT NULL)`), so adding a block adds one.
- **One advisory lock for the store's pages** (`pages:<storeId>`), not one per page: a banner or a curated list is shared by every page that shows it, so their writes must queue with every page's.
- **Cache tags per page** (`page:<storeId>:<pageId>`), with `pages:<storeId>` for store-level content (a banner, the curated lists) and `announcement:<storeId>` for the bar: saving one page's order drops only that page, unless the same save changed the curated lists, which every page shows (`curatedChanged`).
- **API:** the home's procedures became the `page` router: `page.get({ pageId })`, `page.saveLayout({ pageId, … })`, `page.createBanner`/`updateBanner` with the `pageId` their placement is on, `page.deleteBanner` (every page), `page.saveAnnouncement`. No legacy paths (nothing shipped; see below).
- **Migrations, expand only.** The FER-020 tables exist only in this local stack (migration `0018`) and never served a deployed build, but the stack is merged into `qa` one PR at a time, so the reshape is forward and compliant: `0020` adds `page`, `page_section`, `page_cover_banner` and `store.homePageId` (nullable), and relaxes `banner.placement` to nullable and drops its cover check so the new build can insert a banner without it; `0021` (hand-written, fill only, idempotent: a page only for a store with no home, each copy only into a page that has none) copies `home_section` and the cover banners into the home page, a banner between rows that had no place of its own going after the rest, with the categories that had none placed before it in their own order (FER-020's home showed them in that order, and the new build shows a row banner only where a section places it); `0022` makes `homePageId` required. A rename of `home_section` would have broken the build still serving during the deploy, so the old table and columns stay, unread and unwritten, until [FER-061](FER-061-drop-home-only-placing.md) drops them.
- **On QA, merged and deployed one PR at a time:** FER-020's deploy creates the home tables; whatever is curated there until this deploy is copied by `0021` into the home page. While this deploy runs, and for as long as a tab stays pinned to the previous build (`docs/agents/skew-protection.md`), a curation edit made through the previous build writes the old tables, which nothing reads any more: it has to be made again. In that window the two builds also queue their writes on different advisory locks (`home:<storeId>` in the previous one, `pages:<storeId>` here), so a save of the curated lists from each at the same moment can fail on a unique position or lose one of the two; with one admin this is a window of seconds, accepted rather than keeping the old lock's name. Setting the new deployment's Skew Protection Threshold right after the deploy closes that window.
- **A rollback is of the code only; the migrations stay** (expand only, nothing to revert, and the previous build runs on the new schema). In production the build before this release has no home curation (`0018` to `0022` ship in one release), so a rollback there shows what that build always showed. On QA, a rollback to FER-020's build serves the home from its own table and columns as `0021` found them: what this build placed since does not show there (a banner it created has no `placement`, so neither the cover nor the rows list it; a cover or an order it saved is in the page tables), and an edit made there is lost on rolling forward, as in the deploy window above. Nothing is deleted: rolling forward shows this build's placing again. Accepted for QA's test data rather than also writing `placement`, `coverPosition` and `home_section` from this build, a second write path to what FER-061 drops, which for a page other than the home has no meaning.

## Outcome

- **Data** (migrations `0020` to `0022`): `page`, `page_section`, `page_cover_banner`, `store.homePageId`; `banner.placement` nullable; `home_section`, `banner.placement` and `banner.coverPosition` retired (FER-061). The `page` table sits beside the store in `src/server/db/schema/store.ts`, since the two reference each other. `docs/project/data-model.md` § Pages and sections, with how to add a block and a page.
- **Services** (`src/server/services/page.ts`, renamed from `home.ts`): `getPageContent(db, { pageId, … })` (a page the store does not have shows nothing), `getPageCuration(db, { pageId, … })` (each banner's `placement` on that page, `cover`, `rows` or `null`), `findHomePageId`, `createBanner`/`updateBanner`/`deleteBanner`/`savePageLayout` under `lockStorePages`, the page held `FOR KEY SHARE` (NOT_FOUND "Page not found" for another store's or a missing one), a banner listed where it is not on the page refused ("That banner is not on this page").
- **Cache** (`src/server/cache/page.ts`, renamed): `readPageContent(store, pageId, locale)`, `readHomePageId(store)`, `readAnnouncement`; `writeToPage`, `writeToPages`, `writeToAnnouncement` in `src/server/api/utils/write-to-store.ts`.
- **Shared code made page-generic:** `src/lib/page/` (was `src/lib/home/`: `PageContent`, `composePageSections`, `resolvePageSections`, `previewPageContent`), `src/lib/schemas/page`, `src/lib/hooks/page` (`usePageCuration(pageId)`, `useSavePageLayout`), `molecules/store-page-sections`, `molecules/store-page-preview`, `molecules/page-layout-editor`. `organisms/store-home` and `organisms/home-curation` keep their names: they are the home's; the screen takes the page id the route reads.
- **Seed:** the home's banners are placed on the store's home page (`page_cover_banner`, `page_section`); on a home with an order saved and no banner, the two between rows go after that order.
- **Tests:** unit tests follow every rename and cover the page scoping; `src/server/db/drizzle/home-page-migration.integration.test.ts` (the backfill, its order and gaps, replayed twice, and a store that already has its home left alone); the service and router integration tests run against the home page; the e2e `homeEdit` fixture reads the store's home page.
- **Docs:** `docs/project/data-model.md`, `docs/agents/nextjs.md`, `design.md`, `src/e2e/AGENTS.md`.
