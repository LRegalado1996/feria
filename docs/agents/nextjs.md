# Next.js 16

The rules this app's Next configuration imposes. The API reference is `node_modules/next/dist/docs/`; read it before using an API you have not used here.

## Configuration (`next.config.js`)

- `cacheComponents` and `partialPrefetching` are on: every route renders dynamically unless cached, Next prerenders the static part into a shell, and a `<Link>` prefetches that shell ahead of the click.
- `reactCompiler` is on, through Turbopack's native compiler (`experimental.turbopackRustReactCompiler`), so no Babel plugin is installed.
- `output: "standalone"` only off Vercel (`VERCEL !== "1"`): Vercel packages the app itself; standalone is for Docker and CI's e2e runtime.
- Response headers that every deployment target must send (security headers) live in `headers()` here, never in `vercel.json`.
- `images.remotePatterns` allows this deployment's own Blob store and nothing else (`blobImagePatterns`, `src/lib/blob/host.ts`): the host comes from `BLOB_READ_WRITE_TOKEN` at build, over HTTPS, without a query. A build without the token allows no remote image.

## Layouts and pages

- **Never `await` the session, `headers()` or `cookies()` at the top of a layout or page.** A top-level request read holds the whole segment, `{children}` included, behind the request. Put the decision in an async resolver inside `<Suspense>`, with a static fallback above it (`src/app/[locale]/admin/page.tsx`: `AdminHome` → `AdminLanding`). The store's home waits at its top on purpose, for crawlers (§ Store pages).
- A fallback mirrors what it stands for, or stays an empty `aria-busy` canvas when the outcomes differ (signed out vs signed in): a skeleton for the wrong screen is a lie and a layout shift.
- **Layouts are UI chrome.** Auth is decided per page, inside its boundary.
- **The root layout is `src/app/[locale]/layout.tsx`.** `locale` is the one param known at build time (`generateStaticParams` lists both languages), so awaiting it at the top of a layout or page holds nothing behind a request; every other param follows the rule below. Types for `params` are written by hand (`Promise<{ locale: string }>`): nothing here runs `next typegen`, so `PageProps`, `LayoutProps` and `next/root-params` are not available to `pnpm typecheck`.
- **No `export const dynamic`, `revalidate` or `fetchCache`.** Cache with `"use cache"` and an explicit `cacheLife`. `force-static` is inert on a GET route handler under Cache Components: wrap its work in `"use cache"` and check the build's route table (`○`/`◐`/`ƒ`) after the change.
- **`params` and `searchParams` are promises.** Pass the promise into the boundary and await it there. `useParams()`/`useSearchParams()` in a client component need a `<Suspense>` above them.
- **Request-time values:** `Date.now()`, `new Date()`, `Math.random()` and `crypto.randomUUID()` in a server component run after `await connection()` (or another request read) inside a boundary, or move to a client component's effect.
- **Environment gates:** a value fixed per deployment (`VERCEL_ENV`, the branch) can be read at build time. A gate on a value that differs between build and runtime calls `await connection()` first. `export const instant = false` lets a route block on the server but does not stop prerendering.
- **Redirects inside a boundary** arrive after the shell has streamed. An e2e test waits for the destination's content, never for the URL alone.

## Store pages and cached reads

- **The site is one store (FER-038), and its public pages live under `src/app/[locale]/(store)/`**, a route group: `/` is the home, then the catalog pages (FER-043: `/productos`, a group's or a category's `/[group]`, a category in a group's `/[group]/[category]`, all in `(store)/catalog-page.tsx`), an article's `/productos/{slug}` (`articlePath`; no category can be `productos`), `/cart` and `/orders/{token}`, English under `/en` on the same Spanish paths. No address carries a store. The group's layout draws the canvas, `organisms/store-theme`, and reads nothing from the database, so it is prerendered with the build, an article's static page included. The store's colors are code: `src/styles/theme.ts`, written on `<body>` by the root layout (`design.md` § Storefront).
- **The build has no database.** A store page reads the store through `readStore()` only after something request-time: its own dynamic address (an article, an order), the query string (a catalog page), or `await connection()` (the home, the cart's footer). A cached read in the static part of a page runs while the build prerenders it, and fails there.
- **Each page renders its frame and its footer** (FER-039): the frame, `organisms/store-frame`, is the bar (the store's announcement, FER-020: `readAnnouncement`, cached in `src/server/cache/page.ts`; with none on or inside its days the page has no bar) and the header (its categories, from the database), so the layout cannot draw them, for the reason above. A page that reads the store behind a boundary (the cart) hands it `streamedShell(locale)` (`(store)/store-shell.ts`): promises the frame resolves behind boundaries of its own, so the header stays in the static shell, an empty bar holds its place and the announcement and the categories fill in; a page that already read the store awaits `shellOf(store, locale)`, which reads the announcement and the categories before the page renders, so the header's links sit behind no boundary (the home, a catalog page and an order, which wait for their reads; an article: cached reads only); a catalog page hands it the categories it read itself, uncached, so the header, the footer and its filter panel list the same ones; the not-found and error pages render it without either. The footer (`(store)/store-page-footer.tsx`): `StorePageFooter` from the store the page read, with its cached categories, or `StreamedStoreFooter` behind its own boundary on a page that reads nothing else of the store (the cart). Titles end in the store's name the same way (`storeTitle()`, `src/lib/seo/store-metadata.ts`), since the layout has no name to template them with.
- **A cached read lives in `src/server/cache/`**, next to the function that invalidates it. `readStore()` is `"use cache"` with a `cacheLife` and the `store` tag. It calls the service with the app's own `db`, not the oRPC `caller`: that one builds its context from `headers()`, which a cached function may not read.
- **A procedure that writes what a cached read returns invalidates it after the write** (`invalidateStoreCache()` in the `store` router): `revalidateTag(tag, { expire: 0 })`, so the next visit reads the database. `updateTag` only works in a Server Action, and the `"max"` profile would keep serving old texts until someone visits twice.
- **A real 404 needs the lookup to finish before the response starts.** A page whose lookup sits behind `<Suspense>`, or whose route is a shell that streams, is committed to a 200 and shows the not-found page under it. The pages that need a real 404 are `ensureStatic = "navigation"` with one sample `generateStaticParams` that can never be an address (`__sample__`): each address is rendered in full on its first visit and kept, and the page may read nothing request-time. Three do: an article (`/productos/{slug}`: a draft or a deleted article is a 404), the catch-all `(store)/[...rest]`, which answers every address of three segments or more that no page answers, the multi-store site's old ones included (`/lr-market/products/x`), with the store's not-found page, and `(store)/admin/[...rest]`, the same under `/admin` (`/admin/lr-market`). An unknown address of one or two segments (`/lr-market`, `/relojes`, `/bijouterie/relojes`) has a catalog page's shape and reaches it (FER-043): a dynamic segment serves its shell first (Next 16.3+, Partial Prefetching), so a browser gets the not-found page, `noindex`, with a 200, and a category asked outside its group gets its redirect from the browser; a crawler that runs no script gets the page rendered whole, so a real 404 or 308. `/productos`, which has no dynamic segment, is `ƒ` and answers both for real. A page that needs something per request keeps its server output static and loads that part in the browser, or gives up the status code. `src/e2e/tests/store/` holds both.
- **The home (`/`) and the checkout (`/cart`, FER-026, FER-045) always exist** and answer 200: the home reads the store per request before anything is sent (below), the cart behind its footer's boundary. Their metadata waits for the store too, so Next streams it: into `<head>` for a crawler that runs no script, into `<body>` for a browser and Googlebot (`htmlLimitedBots`); the e2e checks both. The cart's contents, their fresh prices (`catalog.cartProducts`) and the checkout live in the browser, one cart per browser. **An order's page (`/orders/{token}`) is per request**: its status changes after it is placed, so it reads `order.getByToken` under `<Suspense>`; a token it does not know, or a malformed one (which costs no query), answers the not-found page with a 200, and the page is `noindex`.
- **What a crawler that runs no script reads (FER-039).** Next never serves an HTML-limited crawler (`htmlLimitedBots`: Bingbot, Twitterbot, Slackbot and the like) the static shell: it renders the page per request, holds the response until the metadata is ready so that it lands in `<head>`, then streams. React writes a boundary's content in place only when it has finished by then and the first response stays under 12,800 bytes with it (`progressiveChunkSize`; a boundary of 500 bytes or less always fits). Otherwise the crawler gets the fallback, and the content comes later in a `<div hidden>` that only a script reveals. The frame alone is about 12 KB, so on a store page only what sits outside every boundary reaches such a crawler. The home therefore waits for the store before anything is sent (`instant = false`): it has no static shell (`ƒ` in the build's route table, not `◐`), and its sections (the cover, the rows and the banners between them, FER-022, or a new store's intro) and its footer sit behind no boundary; `tests/i18n.e2e.ts` reads its metadata with scripts off as Bingbot, and `tests/store/home.serial.e2e.ts` its every section. A client component in it (the cover's carousel, a row) is no boundary: its server HTML is in the first response like the rest; a `<Suspense>` added to the home would hide what it wraps from such a crawler. A catalog page (FER-043, absorbing FER-042) does the same: it reads its address, the store, its categories, its filters and its first page before anything is sent and renders behind no boundary, the header's links included (`tests/store/catalog-pages.e2e.ts` reads a category page with scripts off as Bingbot). What still streams to such a crawler: the cart's footer and an order.
- **An article page (FER-024) keeps the static rule**: its reads are cached in `src/server/cache/catalog.ts` (`readPublishedArticle`, `readRelatedArticles`, `readCategories`, tagged `catalog:<storeId>`), an address no article can have (not a slug, or too long) is answered `null` before the store is read (`couldBeArticle`), so made-up addresses cost neither a query nor an entry and the build's sample reads no database, and every write a shopper would see drops the tag. The article's share card draws only a photo on this site (`ownUrl()`), since its renderer fetches it from the server. Article writes (save, publish, unpublish, availability, delete) and every category write (add, rename, reorder, delete: the frame and the footer of every store page list them) go through `writeToCatalog()` (`src/server/api/utils/write-to-store.ts`), which invalidates after the access-checked write; a write that reaches the storefront only sometimes passes `shows(result)`, as an article's save does (`status === "published"`), so a draft's autosave (FER-017) never empties the cache. Creating an article (always a draft) uses `writeToStore`; a store edit invalidates it too (the page of all articles caches its cover's alt text out of the store's texts). A new write that changes what an article page shows uses `writeToCatalog`.
- **The store's pages (FER-020, FER-058) are cached in `src/server/cache/page.ts`**: `readAnnouncement(store, locale)` (the bar of every store page, an article's static page included), `readHomePageId(store)` (which page `/` shows: the store's `homePageId`) and `readPageContent(store, pageId, locale)` (what a page shows, `PageContent` in `src/lib/page/content.ts`). The home (FER-022) reads its page id, then its content, after `connection()` and the store, beside `shellOf`, and renders it whole in `organisms/store-home`; its structured data is the site (`WebSite`), the store (`Organization`) and an `ItemList` per row (an article spotlight a list of one, named by the article), named as on the page (`src/lib/seo/structured-data.ts`). Tags (each write drops only what it changed, through `src/server/api/utils/write-to-store.ts`): `announcement:<storeId>` for the bar (`writeToAnnouncement`); `page:<storeId>:<pageId>` for one page's order and cover (`writeToPage`); `pages:<storeId>` for what any page may show, a banner, an article spotlight (FER-059) or the curated lists (`writeToPages`, and `writeToPage` when the save changed the lists); `home-page:<storeId>` for the choice of the home; `page-settings:<storeId>` (FER-060) for a page's address, names, status and place in the header, which `readStorePage(store, slug, locale)`, `readHomePage(store, locale)` and `readHeaderPages(store, locale)` carry with `home-page:<storeId>` (`writeToPageSettings` drops it and the pages it names; `writeToHomeChoice`, after `page.setHome`, drops the home's tag, the settings and both pages, since the home's rule fills its blocks in). `readPageContent` also carries `catalog:<storeId>`, so every article and category write that drops the catalog drops it too. The announcement and a page are fresh for an hour at most and never past the next midnight in `America/Montevideo` (`secondsUntilNextBusinessDay`), so a banner or an announcement whose days end leaves the storefront without anyone touching it: the days are `date` columns read against `businessDay(now)` inside the cached function. Going stale is not expiring: the first request after midnight is still answered from the stale entry while it regenerates, so that one response may show yesterday's banner or announcement, and the next shows today's. `expire` stays a day on purpose: clamped to midnight it would make the read a dynamic hole in the last minutes before midnight (FER-020's decisions).
- **A page built from sections (FER-060) shares `/[group]` with the catalog**: the route asks `resolveStorePage` (`(store)/store-page-view.tsx`, read once per request with `React.cache`, after `connection()`) whether the store has a page at that address, and answers the catalog's page otherwise. The page renders like the home, whole and behind no boundary (`organisms/store-page`: its cover, its blocks, its name the `h1`, visually hidden under a cover), with its own metadata (its texts for search engines, else made from its name), canonical, `hreflang` and trail (`BreadcrumbList`, plus an `ItemList` per block, `(store)/section-lists.ts`, shared with the home). A draft is not there for the public, so the address falls to the catalog's not-found page; a signed-in admin (`isAdminRequest`, checked on the server) sees it with a note and `noindex`. The home's own address, whichever page it is (`/home` at first), redirects to `/` (`/en` under `/en`); a page that stops being the home answers at its address again. Statuses follow the rule above for one segment: a browser gets the not-found page with a 200 and the redirect from the browser, a crawler that runs no script a real 404 or 307 (`tests/admin/pages.serial.e2e.ts`). `/`'s metadata takes the home page's own title and description for search engines when it has them (`readHomePage`), else the store's; its `h1` stays the store's name. The sitemap and `llms.txt` list each published page but the home once (`listIndexablePages`). The header lists the published pages the admin shows there, before the categories (`readHeaderPages`, `(store)/store-shell.ts`): the computer's line has room for what fits and no menu, and a category left off it is still in the catalog's filter, a page would be nowhere.
- **A catalog page (FER-023, FER-043) renders per request**, because its first criterion is a server-rendered first page with its own title for every selection, and the filters, the search and the sort are the query string; the category is the path. It reads its params and `searchParams` at its top, behind no boundary (`instant = false`), then the store, the category's page (`readCategoryPage`, cached: its names, its group, its categories, its texts, its cover), the categories and filters (uncached) and its first page; the metadata reads the same, once (`React.cache`). A link's selection is read with `readCatalogQuery()` (`src/lib/catalog/query.ts`), which drops anything malformed before it reaches the API. A later page of a list (FER-044) is the same page with `?cursor=` (the sort's key, a dot and the id, `readCatalogCursor()`): the "Cargar más" link a visitor without the script or a crawler follows renders the articles after it, behind no boundary like the first page, `noindex, follow`, its canonical the list's first page; with the script the link loads in place and the grid keeps loading as it scrolls. A cursor that does not read is the first page. A browser pays for it: the page has no static shell to show while it reads. A category page's own texts come from the admin, else from `src/content` (`categoryDescription`, `groupDescription`); its cover is its share card. Choosing a category in the filter panel leads to another page, so the panel closes, at once (the page left behind stays mounted, hidden: § Navigation).
- **The coming-soon page (`/coming-soon`, FER-034)** lives outside `(store)`: no frame, no notice. It renders per request (`ƒ`, `instant = false`): after `await connection()` it reads what an admin saved through `readComingSoon()` (`src/server/cache/coming-soon.ts`, tagged `coming-soon`, invalidated by both of the admin's writes) before anything is sent, since its texts are its whole first screen, and the store's social links through `readStore()` (the brand's, `SOCIAL_LINKS`, where the store has none). A read that fails is reported (`ComingSoon.read_page`, `ComingSoon.read_store`) and the page says the dictionary's texts and links the brand's profiles: the proxy sends the public here when it cannot read the switch either, so the page stands through an outage. Its metadata is the dictionary's and needs no read. The countdown reads the request's clock inside its own `<Suspense>`.

## Navigation

- **After signing in, signing up or signing out, navigate with a full page load** (`window.location.assign(target)`), never `router.refresh()`/`router.push()`. A soft navigation can keep a shell rendered for the old session, or settle on the URL of a server-redirect chain without its content.
- **Changing language is a soft navigation** (`molecules/locale-toggle` is a `<Link>`): the `[locale]` layout re-renders under the new param, `<html lang>` updates and the theme class stays.
- **Routes stay mounted.** Cache Components keeps a route you navigate away from inside React's `<Activity mode="hidden">`: its state survives, its effects are cleaned up and re-run on return, and its DOM stays in the document, so a global `:has()` selector or a `document.querySelector` can match a hidden tree.

## React Compiler

- Components are memoized automatically; don't add `useMemo`/`useCallback` for render cost.
- A component that reads a library's mutable instance during render (TanStack Table's `getRowModel()`, `getHeaderGroups()`) starts with `"use no memo"`: the compiler cannot see the mutation and skips the re-render.
- react-hook-form: bind fields through `<FormField>` (a `Controller`, re-registered by its own hook), never a `{...register("field")}` spread: `reset()` forgets every registered field, a memoized spread never registers it again, and what the user types next is lost on submit. Read form state with `useFormState`/`useWatch`, never `form.formState`/`form.watch()`: a read off the stable `form` object is memoized and goes stale. A form whose schema changes is keyed and remounted, not reset. The escape hatch for a library the compiler cannot follow is `"use no memo"` as the component's first statement.
- An impure call in render (`Date.now()`, `Math.random()`) is memoized as if it were pure. Pass time in as a prop or state (`useNow`).
- Compiler regressions do not show in unit tests (Vitest does not run the compiler). Only e2e against a production build (`pnpm e2e:ci`) catches them.

## Hydration

The server renders at one instant and the browser hydrates later; React throws away the server HTML for any subtree whose first client render differs.

- A client component's first render reads nothing the server could not: no `Date.now()`, `Math.random()`, `window`, `localStorage` or time-zone-dependent formatting. Seed a clock from the server's instant and switch after mount: `useNow(renderedAt)` (`src/lib/hooks/ui/use-now.ts`), as the orders' relative times do.
- A remembered client preference (`localStorage`) never changes the first client render: read it with `useSyncExternalStore` and a `null` server snapshot, and keep the region's skeleton until it resolves.
- A value several client components read from the query cache is seeded at a shared ancestor above all of them: React hydrates whichever boundary the user touches first.
- A Suspense fallback or `loading.tsx` declares the same structure as the page it stands for.
- Tests: a component whose output depends on the clock gets a unit test with `collectHydrationErrors` (`src/test/hydration.ts`), which server-renders at one instant and hydrates at a later one; `renderHook` and `render` never hydrate. `src/e2e/tests/hydration.e2e.ts` fails on any hydration error in the browser console.

## Proxy

`src/proxy.ts` (formerly `middleware.ts`) does three things: it stamps `/api` requests with a request id for logging, it applies the coming-soon switch to page requests (below), and it routes page requests by language (`docs/agents/i18n.md`): unprefixed paths are rewritten to `/es/...`, `/es/...` redirects to the unprefixed URL, `/en/...` passes through. Its `matcher` is one constant pattern that leaves out Next's assets, Vercel's endpoints, the Sentry tunnel, the generated brand images, the root metadata routes (`/robots.txt`, `/sitemap.xml`: rewritten to `/es/...` they would be a 404) and the files in `public/`, by name or by folder; a new top-level path that must not get a language is added there.

**The coming-soon switch is the one access decision the proxy makes** (FER-034), and it makes it for real, never on a cookie's presence:

- **The switch.** `isStorefrontClosed()` (`src/server/cache/storefront-switch.ts`) reads `coming_soon.published` (no row is published). Next runs no `"use cache"` in the proxy, and the proxy shares no memory with the function that saves, so no tag reaches it: the read is remembered for 5 seconds per server (`SWITCH_TTL_MS`), counted from when it was asked, one read at a time however many requests arrive, and a flip from the admin reaches every server within that window. It fails closed: a read that throws or takes over 5 seconds (`SWITCH_TIMEOUT_MS`, raced with `within()` from `src/lib/utils/within.ts`) is reported (`ComingSoon.read_switch`) and counts as published for a window from the failure, so an outage hides the store instead of opening it, at one wait per window. The query itself runs under a 4-second `statement_timeout` (`withStatementTimeout`, `src/server/db/statement-timeout.ts`), so Postgres cancels a stalled read and frees its connection before the next window starts another. The admin's pages never read it.
- **Published:** every page request but `/admin/...` and `/coming-soon` itself gets a 307 to `/coming-soon` in its language, without its query and with `Cache-Control: private, no-store`, unless `isAdminRequest()` (`src/server/better-auth/admin-request.ts`) vouches for a signed-in admin: the session's token looked up in the database past Better Auth's cookie cache, the login re-read as `adminProcedure` does. A request without a session cookie answers no without a query, so the public costs the database nothing; a check that throws or takes over the switch's 5 seconds is reported (`ComingSoon.check_admin`) and answers no. The coming-soon page gives its own two reads the same limit and falls back to the dictionary's texts and the brand's links. **Not published:** `/coming-soon` leads home with the same 307, except for an admin, who may preview it.
- **Nothing cached depends on who asked.** An admin let through gets exactly the server output the public would: the strip that says the store is closed (`molecules/store-preview-notice`, in the `(store)` layout) is drawn in the browser from a cookie the proxy sets on such a response (`STORE_PREVIEW_COOKIE`, `lr-store-preview`, readable by scripts, granting nothing) and clears from any other page response that carries it. So no page holds a version for one viewer, a cache filled by an admin's visit (an article's page, rendered once and kept) is the public's page, and since the proxy runs before every cache (`node_modules/next/dist/docs/01-app/02-guides/cdn-caching.md`), a closed store's cached pages never reach the public. A response that sets the cookie is not stored by a shared cache either.
- The API and the health check are never behind the switch; `order.create` checks it itself (the cached `readComingSoon()`, which a flip invalidates at once) and takes orders while closed only from an admin (`isAdminRequest`).

Every other access decision is made per page and per procedure.

`usePathname()` can return the rewritten path (`/es/...`) on the server and the browser's on the client. Render only what does not depend on that prefix: the result of `localizePath()`, or the `pathname` `splitLocale()` returns. Never the `locale` it returns (`"es"` for the rewritten path, `null` for the browser's): the page's language comes from `useLocale()`.
