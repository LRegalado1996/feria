# Next.js 16

The rules this app's Next configuration imposes. The API reference is `node_modules/next/dist/docs/`; read it before using an API you have not used here.

## Configuration (`next.config.js`)

- `cacheComponents` and `partialPrefetching` are on: every route renders dynamically unless cached, Next prerenders the static part into a shell, and a `<Link>` prefetches that shell ahead of the click.
- `reactCompiler` is on, through Turbopack's native compiler (`experimental.turbopackRustReactCompiler`), so no Babel plugin is installed.
- `output: "standalone"` only off Vercel (`VERCEL !== "1"`): Vercel packages the app itself; standalone is for Docker and CI's e2e runtime.
- Response headers that every deployment target must send (security headers) live in `headers()` here, never in `vercel.json`.
- `images.remotePatterns` allows this deployment's own Blob store and nothing else (`blobImagePatterns`, `src/lib/blob/host.ts`): the host comes from `BLOB_READ_WRITE_TOKEN` at build, over HTTPS, without a query. A build without the token allows no remote image.

## Layouts and pages

- **Never `await` the session, `headers()` or `cookies()` at the top of a layout or page.** A top-level request read holds the whole segment, `{children}` included, behind the request. Put the decision in an async resolver inside `<Suspense>`, with a static fallback above it (`src/app/[locale]/admin/page.tsx`: `AdminHome` → `AdminLanding`). The store's home waits at its top on purpose, for crawlers (§ Store pages).
- A fallback mirrors what it stands for, or stays an empty `aria-busy` canvas when the outcomes differ (signed out vs signed in): a skeleton for the wrong screen is a lie and a layout shift.
- **Layouts are UI chrome.** Auth is decided per page, inside its boundary.
- **The root layout is `src/app/[locale]/layout.tsx`.** `locale` is the one param known at build time (`generateStaticParams` lists both languages), so awaiting it at the top of a layout or page holds nothing behind a request; every other param follows the rule below. Types for `params` are written by hand (`Promise<{ locale: string }>`): nothing here runs `next typegen`, so `PageProps`, `LayoutProps` and `next/root-params` are not available to `pnpm typecheck`.
- **No `export const dynamic`, `revalidate` or `fetchCache`.** Cache with `"use cache"` and an explicit `cacheLife`. `force-static` is inert on a GET route handler under Cache Components: wrap its work in `"use cache"` and check the build's route table (`○`/`◐`/`ƒ`) after the change.
- **`params` and `searchParams` are promises.** Pass the promise into the boundary and await it there. `useParams()`/`useSearchParams()` in a client component need a `<Suspense>` above them.
- **Request-time values:** `Date.now()`, `new Date()`, `Math.random()` and `crypto.randomUUID()` in a server component run after `await connection()` (or another request read) inside a boundary, or move to a client component's effect.
- **Environment gates:** a value fixed per deployment (`VERCEL_ENV`, the branch) can be read at build time. A gate on a value that differs between build and runtime calls `await connection()` first. `export const instant = false` lets a route block on the server but does not stop prerendering.
- **Redirects inside a boundary** arrive after the shell has streamed. An e2e test waits for the destination's content, never for the URL alone.

## Store pages and cached reads

- **The site is one store (FER-038), and its public pages live under `src/app/[locale]/(store)/`**, a route group: `/` is the home, then the catalog pages (FER-043: `/productos`, a group's or a category's `/[group]`, a category in a group's `/[group]/[category]`, all in `(store)/catalog-page.tsx`), an article's `/productos/{slug}` (`articlePath`; no category can be `productos`), `/cart` and `/orders/{token}`, English under `/en` on the same Spanish paths. No address carries a store. The group's layout draws the canvas, `organisms/store-theme`, and reads nothing from the database, so it is prerendered with the build, an article's static page included. The store's colors are code: `src/styles/theme.ts`, written on `<body>` by the root layout (`design.md` § Storefront).
- **The build has no database.** A store page reads the store through `readStore()` only after something request-time: its own dynamic address (an article, an order), the query string (a catalog page), or `await connection()` (the home, the cart's footer). A cached read in the static part of a page runs while the build prerenders it, and fails there.
- **Each page renders its frame and its footer** (FER-039): the frame, `organisms/store-frame`, is the bar (a fixed notice from the dictionaries until FER-020, handed over as a promise like the categories so FER-020 can read it from the store) and the header (its categories, from the database), so the layout cannot draw them, for the reason above. A page that reads the store behind a boundary (the cart) hands it `streamedShell(locale)` (`(store)/store-shell.ts`): promises the frame resolves behind boundaries of its own, so the header stays in the static shell, an empty bar holds its place and the categories fill in; a page that already read the store awaits `shellOf(store, locale)`, which reads the categories before the page renders, so the header's links sit behind no boundary (the home, a catalog page and an order, which wait for their reads; an article: cached reads only); a catalog page hands it the categories it read itself, uncached, so the header, the footer and its filter panel list the same ones; the not-found and error pages render it without either. The footer (`(store)/store-page-footer.tsx`): `StorePageFooter` from the store the page read, with its cached categories, or `StreamedStoreFooter` behind its own boundary on a page that reads nothing else of the store (the cart). Titles end in the store's name the same way (`storeTitle()`, `src/lib/seo/store-metadata.ts`), since the layout has no name to template them with.
- **A cached read lives in `src/server/cache/`**, next to the function that invalidates it. `readStore()` is `"use cache"` with a `cacheLife` and the `store` tag. It calls the service with the app's own `db`, not the oRPC `caller`: that one builds its context from `headers()`, which a cached function may not read.
- **A procedure that writes what a cached read returns invalidates it after the write** (`invalidateStoreCache()` in the `store` router): `revalidateTag(tag, { expire: 0 })`, so the next visit reads the database. `updateTag` only works in a Server Action, and the `"max"` profile would keep serving old texts until someone visits twice.
- **A real 404 needs the lookup to finish before the response starts.** A page whose lookup sits behind `<Suspense>`, or whose route is a shell that streams, is committed to a 200 and shows the not-found page under it. The pages that need a real 404 are `ensureStatic = "navigation"` with one sample `generateStaticParams` that can never be an address (`__sample__`): each address is rendered in full on its first visit and kept, and the page may read nothing request-time. Three do: an article (`/productos/{slug}`: a draft or a deleted article is a 404), the catch-all `(store)/[...rest]`, which answers every address of three segments or more that no page answers, the multi-store site's old ones included (`/lr-market/products/x`), with the store's not-found page, and `(store)/admin/[...rest]`, the same under `/admin` (`/admin/lr-market`). An unknown address of one or two segments (`/lr-market`, `/relojes`, `/bijouterie/relojes`) has a catalog page's shape and reaches it (FER-043): a dynamic segment serves its shell first (Next 16.3+, Partial Prefetching), so a browser gets the not-found page, `noindex`, with a 200, and a category asked outside its group gets its redirect from the browser; a crawler that runs no script gets the page rendered whole, so a real 404 or 308. `/productos`, which has no dynamic segment, is `ƒ` and answers both for real. A page that needs something per request keeps its server output static and loads that part in the browser, or gives up the status code. `src/e2e/tests/store/` holds both.
- **The home (`/`) and the checkout (`/cart`, FER-026, FER-045) always exist** and answer 200: the home reads the store per request before anything is sent (below), the cart behind its footer's boundary. Their metadata waits for the store too, so Next streams it: into `<head>` for a crawler that runs no script, into `<body>` for a browser and Googlebot (`htmlLimitedBots`); the e2e checks both. The cart's contents, their fresh prices (`catalog.cartProducts`) and the checkout live in the browser, one cart per browser. **An order's page (`/orders/{token}`) is per request**: its status changes after it is placed, so it reads `order.getByToken` under `<Suspense>`; a token it does not know, or a malformed one (which costs no query), answers the not-found page with a 200, and the page is `noindex`.
- **What a crawler that runs no script reads (FER-039).** Next never serves an HTML-limited crawler (`htmlLimitedBots`: Bingbot, Twitterbot, Slackbot and the like) the static shell: it renders the page per request, holds the response until the metadata is ready so that it lands in `<head>`, then streams. React writes a boundary's content in place only when it has finished by then and the first response stays under 12,800 bytes with it (`progressiveChunkSize`; a boundary of 500 bytes or less always fits). Otherwise the crawler gets the fallback, and the content comes later in a `<div hidden>` that only a script reveals. The frame alone is about 12 KB, so on a store page only what sits outside every boundary reaches such a crawler. The home therefore waits for the store before anything is sent (`instant = false`): it has no static shell (`ƒ` in the build's route table, not `◐`), and its intro and footer sit behind no boundary; `tests/i18n.e2e.ts` reads it with scripts off as Bingbot and requires it visible. A catalog page (FER-043, absorbing FER-042) does the same: it reads its address, the store, its categories, its filters and its first page before anything is sent and renders behind no boundary, the header's links included (`tests/store/catalog-pages.e2e.ts` reads a category page with scripts off as Bingbot). What still streams to such a crawler: the cart's footer and an order.
- **An article page (FER-024) keeps the static rule**: its reads are cached in `src/server/cache/catalog.ts` (`readPublishedArticle`, `readRelatedArticles`, `readCategories`, tagged `catalog:<storeId>`), an address no article can have (not a slug, or too long) is answered `null` before the store is read (`couldBeArticle`), so made-up addresses cost neither a query nor an entry and the build's sample reads no database, and every write a shopper would see drops the tag. The article's share card draws only a photo on this site (`ownUrl()`), since its renderer fetches it from the server. Article writes (update, publish, unpublish, availability, delete, photo order) and every category write (add, rename, reorder, delete: the frame and the footer of every store page list them) go through `writeToCatalog()` (`src/server/api/utils/write-to-store.ts`), which invalidates after the access-checked write; a store edit invalidates it too (its currency shows on every price). A new write that changes what an article page shows uses `writeToCatalog`.
- **A catalog page (FER-023, FER-043) renders per request**, because its first criterion is a server-rendered first page with its own title for every selection, and the filters, the search and the sort are the query string; the category is the path. It reads its params and `searchParams` at its top, behind no boundary (`instant = false`), then the store, the category's page (`readCategoryPage`, cached: its names, its group, its categories, its texts, its cover), the categories and filters (uncached) and its first page; the metadata reads the same, once (`React.cache`). A link's selection is read with `readCatalogQuery()` (`src/lib/catalog/query.ts`), which drops anything malformed before it reaches the API. A later page of a list (FER-044) is the same page with `?cursor=` (the sort's key, a dot and the id, `readCatalogCursor()`): the "Cargar más" link a visitor without the script or a crawler follows renders the articles after it, behind no boundary like the first page, `noindex, follow`, its canonical the list's first page; with the script the link loads in place and the grid keeps loading as it scrolls. A cursor that does not read is the first page. A browser pays for it: the page has no static shell to show while it reads. A category page's own texts come from the admin, else from `src/content` (`categoryDescription`, `groupDescription`); its cover is its share card. Choosing a category in the filter panel leads to another page, so the panel closes, at once (the page left behind stays mounted, hidden: § Navigation).

## Search engines and AI assistants

- **Where each surface lives (FER-024):** `src/app/sitemap.ts` (`/sitemap.xml`: the store's home, all articles, each group and category page with a published article (FER-043), and the published articles, in Spanish and English with `hreflang` alternates), `src/app/robots.ts` (`/robots.txt`: everyone allowed, the AI crawlers named, `/admin`, `/api/` and `/coming-soon` disallowed in both languages, each root anchored with `$` so an address that only starts alike (`/apio`) stays crawlable and its query (`/admin?next=…`) disallowed by a `?` rule, the sitemap declared) and `src/app/[locale]/(store)/llms.txt/route.ts` (`/llms.txt` and `/en/llms.txt`, built by `src/lib/seo/llms.ts`, a link to every group and category page, its text in `src/content/{es,en}/seo.ts`). Absolute URLs come from `siteOrigin()` / `absoluteUrl()` (`src/lib/seo/origin.ts`), the origin the root layout's `metadataBase` uses.
- **A draft is never listed.** Every read goes through `src/server/services/seo.ts`, whose queries hold that rule (its integration test proves it); a new surface reads from there, never from the catalog's admin queries.
- **The sitemap and `llms.txt` read at request time** (`connection()`), so a new article is listed at once and the build needs no database. While the storefront is closed the sitemap is empty and the proxy sends `llms.txt` to the coming-soon page; `robots.txt` is served either way.

## Admin pages

- **Every admin page checks for itself** (FER-013), inside its `<Suspense>` boundary and above any data: `requireAdmin(returnTo, locale)` (`src/lib/admin/access.ts`) answers the login (`admin.me`, re-read from the database) or redirects to `/admin/sign-in?next=<returnTo>`. Every login is an admin and reaches every section (FER-038), so that is the whole check. The `admin` layout only sets the metadata (no index).
- **One section, one folder:** `/admin/{products,categories,filters,orders,home,settings,users,metrics}` are static folders (the ones whose screen is still to come render `admin-section-placeholder.tsx`), and `/admin` sends a signed-in login to the orders. There is no `[section]` segment: `dynamicParams` is not available with Cache Components, and a static folder is what lets any other address under `/admin` reach the catch-all and its real 404.
- **The page renders `organisms/admin-shell`** with the login `requireAdmin` answered (its name and email at the foot of the sections), one list of sections for every login; the navigation is not the authorization. Its screen renders `molecules/admin-page`, the sticky top bar with the page's one heading and its actions, over the content (`design.md` § Admin).
- **Params are read inside the boundary.** An order's id is per request, so its page passes `params` into its resolver; the fallback is `molecules/admin-shell-skeleton`, a client component that reads the language from the provider.
- **A refused admin page renders the not-found page with a 200** (an order the store does not have): the check happens after the shell started streaming (the session is a request-time read), so the status is committed; what the user sees, and what the e2e asserts, is the not-found page.
- **The orders pages (FER-027)** read their selection from `searchParams` inside the boundary (`readOrdersQuery`, `src/lib/admin/orders.ts`: an unknown status is all of them) and put the `HydrationBoundary` above `AdminShell`, so the navigation's count of orders to pack (`molecules/orders-pending-badge`) and the screen's tabs hydrate from the same prefetched counts. An order's page checks its id is a positive int before any session check or query (`readOrderId`), and answers the not-found page for an order the store does not have (`catchNotFound`); any other failed read renders the screen, which fetches again.
- **`?next=` is untrusted:** `safeReturnPath` (`src/lib/admin/paths.ts`) keeps it only when it is an admin page of this site, never the sign-in page or another host.

## Navigation

- **After signing in, signing up or signing out, navigate with a full page load** (`window.location.assign(target)`), never `router.refresh()`/`router.push()`. A soft navigation can keep a shell rendered for the old session, or settle on the URL of a server-redirect chain without its content.
- **Changing language is a soft navigation** (`molecules/locale-toggle` is a `<Link>`): the `[locale]` layout re-renders under the new param, `<html lang>` updates and the theme class stays.
- **Routes stay mounted.** Cache Components keeps a route you navigate away from inside React's `<Activity mode="hidden">`: its state survives, its effects are cleaned up and re-run on return, and its DOM stays in the document, so a global `:has()` selector or a `document.querySelector` can match a hidden tree.

## React Compiler

- Components are memoized automatically; don't add `useMemo`/`useCallback` for render cost.
- A component that reads a library's mutable instance during render (TanStack Table's `getRowModel()`, `getHeaderGroups()`) starts with `"use no memo"`: the compiler cannot see the mutation and skips the re-render.
- react-hook-form: bind fields through `<FormField>` (a `Controller`, re-registered by its own hook), never a `{...register("field")}` spread: `reset()` forgets every registered field, a memoized spread never registers it again, and what the user types next is lost on submit. Read form state with `useFormState`/`useWatch`, never `form.formState`/`form.watch()`: a read off the stable `form` object is memoized and goes stale. A form whose schema changes is keyed and remounted, not reset. The escape hatch for a library the compiler cannot follow is `"use no memo"` as the component's first statement.
- An impure call in render (`Date.now()`, `Math.random()`) is memoized as if it were pure. Pass time in as a prop or state (`useNow`).
- Compiler regressions do not show in unit tests (Vitest does not run the compiler). Only e2e against a production build (`pnpm e2e:ci`) catches them.

## Hydration

The server renders at one instant and the browser hydrates later; React throws away the server HTML for any subtree whose first client render differs.

- A client component's first render reads nothing the server could not: no `Date.now()`, `Math.random()`, `window`, `localStorage` or time-zone-dependent formatting. Seed a clock from the server's instant and switch after mount: `useNow(renderedAt)` (`src/lib/hooks/ui/use-now.ts`), as the orders' relative times do.
- A remembered client preference (`localStorage`) never changes the first client render: read it with `useSyncExternalStore` and a `null` server snapshot, and keep the region's skeleton until it resolves.
- A value several client components read from the query cache is seeded at a shared ancestor above all of them: React hydrates whichever boundary the user touches first.
- A Suspense fallback or `loading.tsx` declares the same structure as the page it stands for.
- Tests: a component whose output depends on the clock gets a unit test with `collectHydrationErrors` (`src/test/hydration.ts`), which server-renders at one instant and hydrates at a later one; `renderHook` and `render` never hydrate. `src/e2e/tests/hydration.e2e.ts` fails on any hydration error in the browser console.

## Proxy

`src/proxy.ts` (formerly `middleware.ts`) does three things and decides no access: it stamps `/api` requests with a request id for logging, it sends page requests to `/coming-soon` with a 307 while the launch switch is off (`src/lib/env/launch.ts`; the admin and the API are never behind it), and it routes page requests by language (`docs/agents/i18n.md`): unprefixed paths are rewritten to `/es/...`, `/es/...` redirects to the unprefixed URL, `/en/...` passes through. Its `matcher` is one constant pattern that leaves out Next's assets, Vercel's endpoints, the Sentry tunnel, the generated brand images, the root metadata routes (`/robots.txt`, `/sitemap.xml`: rewritten to `/es/...` they would be a 404) and the files in `public/`, by name or by folder; a new top-level path that must not get a language is added there. If it ever redirects on a session cookie, that is optimistic only: pages and procedures still check the session themselves.

`usePathname()` can return the rewritten path (`/es/...`) on the server and the browser's on the client. Render only what does not depend on that prefix: the result of `localizePath()`, or the `pathname` `splitLocale()` returns. Never the `locale` it returns (`"es"` for the rewritten path, `null` for the browser's): the page's language comes from `useLocale()`.
