# E2E tests

Scoped rules for `src/e2e/`. `CLAUDE.md` beside this file is a symlink to it. Selectors, file layout and commands: `docs/agents/testing.md` § E2E tests.

## Failure first

- `retries: 0`, locally and in CI. A retry-pass is a defect report thrown away: a race the retry hides ships. Never "fix" a failure by padding a timeout, adding a fixed wait or re-running until green.
- CI keeps a trace of every failed test (`trace: retain-on-failure`, with DOM snapshots) and a screenshot; no video, the trace has a screencast. It stops after 10 failures and ends the run before the job's time limit, so a broken boot still reports.
- The browser runs in `UTC` (`timezoneId`) and so do the runner, its workers and the app server it starts (`TZ`).
- A test that legitimately needs more than the 90 s budget calls `test.slow()`; the budget is not padded.

## One user per worker; own the rows you touch

Tests run fully parallel in the `chromium` project (`fullyParallel: true`; workers from `E2E_WORKERS`, else up to 4 and at most cores - 1 on CI). That is safe only because:

- **Each worker signs in as its own user.** `fixtures/user.fixture.ts` gets or creates `e2e-w<index>@example.com` through Better Auth's server API once per worker, signs it in over HTTP and keeps the cookies. Every login is an admin (FER-038), so it reaches the whole admin. `authenticatedPage` and the default `page` use them; `freshAuthenticatedPage` signs in anew (sign-out tests end only that session); `identity` says who the user is. There is no setup project. A spec that starts signed out sets `test.use({ storageState: { cookies: [], origins: [] } })`.
- **The site is one store, and every spec shares it** (FER-038): the row the migrations create, whose id is `db.storeId`. A test seeds its rows into it (`db.seed.createCategory`, `createArticle`, `createFilter`, `createLogin`), every name and slug ending in its own tag (`uniqueTag()`, a whole `crypto.randomUUID()`), and orders from a phone of its own (`uniquePhone()`: the hourly limit and the search count a phone across the store). It asserts only on its own rows: the catalog through its own category's page (`/<slug>`, FER-043), its own filter or a search for its tag; an admin list by its own names; an order by its code or its phone. Never a position, a count or an empty list across the store.
- **The store's settings are global and fixed for the run.** As each worker starts, the worker fixture `storeSettings` writes `STORE_SETTINGS` (`fixtures/store-settings.ts`: the name `E2E Market`, texts in both languages, Instagram and WhatsApp, no TikTok; the currency is not a setting, FER-014, and stays the pesos the migrations give the store) through `store.update` as its user: the same values in every worker, so workers converge, and the edit drops whatever a previous run left cached. The same fixture writes the run's announcement bar, `STORE_ANNOUNCEMENT` (the Paseo Prado wording, on, no days, no link), through `page.saveAnnouncement` (FER-020). Specs assert those values and never set their own. A run against a development database (`pnpm e2e` beside `pnpm dev`) leaves the store with them.
- **Teardown deletes exactly what the test created**, in the `db` fixture (automatic for every test), by the ids captured as each insert returned, and by the ids read off the responses that created a row through the UI (`createdRows`: a category, a filter or a value from the admin's forms, an article the wizard created from its first photo, an order from the checkout): first the orders holding the test's articles (an order line's article turns null once the article goes, and nothing would find the order then), then the articles, the filters, the categories and the logins. Never the store. Never by name prefix or `LIKE`: those match a parallel worker's rows. Never in a test-body `finally`. Sign-up is closed (FER-009): a spec that needs another login seeds it.
- **A hand-made `browser.newContext()`** gets none of the config's `use` options: pass `baseURL: requireBaseURL(baseURL)` and `ignoreHTTPSErrors: IGNORE_HTTPS_ERRORS` from `../fixtures`. Its responses are not read, so it only reads: it creates nothing teardown would have to find.
- **Better Auth's per-IP sign-in limit is off on the server Playwright starts** (`E2E_DISABLE_AUTH_RATE_LIMIT` in `webServer.env`, ignored on a production deploy): every worker signs in from one machine.
- **The coming-soon switch is real, and the `closed` project owns it** (FER-034). It is a row in the database (no row is published, so CI's fresh database starts closed), flipped through the admin's API; there is no test-only override. Every worker's `storefrontSwitch` (a worker fixture, automatic) puts it where its project's `storefront` option says and waits until the public sees it: `open` everywhere but the `closed` project, whose specs (`*.closed.e2e.ts`) run first, alone (`workers: 1`), with the page published and every text empty, and whose worker takes the page down again when it ends. A test there that edits the page or flips the switch asks for `comingSoonEdit` (refused anywhere else), which writes the closed, empty page back when it ends. The proxy remembers the switch for up to 5 seconds per server, so after a flip wait for the public to see it (`waitForStorefront`, `expect.poll`), never for a fixed time. Inside a test a new request context takes the config's `use`, the worker's session included, and an admin sees the closed store: a visitor's context passes `storageState: { cookies: [], origins: [] }`.
- **Shared state runs alone.** Design it away first: scope to the test's own rows. A spec that changes what every spec reads, or needs the store's whole list, gets a `*.serial.e2e.ts` name, and the `serial` project runs it alone (`workers: 1`) after the `closed` project (above) and before the parallel project, which depends on it. Today: the home's curation and the storefront's home (`tests/admin/home-curation.serial.e2e.ts` and `tests/store/home.serial.e2e.ts`, FER-020, FER-022, through the `homeEdit` fixture, which reads the store's home page (FER-058) and snapshots `page.get` for it, saves its order (`saveLayout`, which drops that page's cache: a row seeded straight into the database shows only after it) and can leave the home nothing to show (`hideEverything`: every published article a draft, every banner off), and, when the test ends, shows again what it hid, deletes the banners it added, saves the order back and writes `STORE_ANNOUNCEMENT` again; the banners a test seeds with `db.seed.createBanner` use the seed's photos, which `next/image` serves without the Blob store; a test places its own sections first and asserts on them, since a development database holds the seed's home too), the store's settings (`tests/store/store-settings.serial.e2e.ts` and the settings screen's `tests/admin/settings.serial.e2e.ts`, through the `storeEdit` fixture, which writes `STORE_SETTINGS` back when the test ends and refuses a spec that is not serial), reordering categories (the server refuses a partial list), and the orders' tab counts and the navigation's badge of orders to pack, which count every order and assume a store with none but the test's, as `pnpm e2e:ci` and CI give them. A failed serial test skips the parallel project. Playwright runs a dependency project in full under a file filter and never repeats it under `--repeat-each`: to repeat serial specs, name only them (or pass `--project=serial`), apart from the parallel ones.

## Readiness: wait for what the next step needs

Visible is not ready. A server-rendered control shows before React owns it, and a click or keystroke that lands first vanishes. `networkidle` proves nothing either (a polling page never idles), and a fixed wait passes on a fast machine and fails on a slow one. Both are ratchets held at zero (`e2e-networkidle`, `e2e-fixed-delay`).

- **Page loaded:** `page.goto()` then the page object's `waitForLoad()`, which waits for the page's own content (`loaded()`).
- **The language toggle's link** carries the query string only once React has read the URL (the prerendered shell is the same for every query): assert its `href` before clicking. After the switch the page left behind stays mounted and hidden with a toggle of its own, so target the visible one (`AdminPage.localeToggle()`).
- **First harmless open after a load** (a menu, a mode switch, a dialog): `BasePage.clickUntilVisible(trigger, ready)` (`fixtures/click-until-visible.ts`). It waits for the trigger once, outside the loop, then re-clicks only while `ready` is absent, each try bounded at 5 s. Never on a submit: a second submit commits twice.
- **A request that must happen:** `completeRpcAction(page, "/api/orpc/category/create", action, { input })` (`fixtures/complete-rpc-action.ts`, Better Auth paths too). It arms the response wait before acting, matches the path and the input, requires the status (200 unless you pass the refusal you expect) and the whole response. Then assert what rendered. A lost click then fails at the request, not as a missing element 60 s later.
- **A form React must own before you type:** wait for the control only React enables (the auth form's submit button, `AdminSignInPage.waitForForm()`), or fill inside `toPass` until it is.
- **An absent result** is meaningful only after the operation that would have produced it completed and rendered.

## Three interaction races this suite is built around

- **Landed before ready.** The first interaction after a navigation hits a visible, not yet hydrated control and is silently lost; the test then waits out its whole timeout. Guard it as above.
- **Closed is not removed.** A dismissed dialog's overlay animates out separately and, while transparent, still intercepts clicks; its close autofocus fires late and steals focus. After closing the last dialog, `expectDialogRemoved(page, dialog)` (`fixtures/expect-dialog-removed.ts`) waits for the content and the `dialog-overlay` to be gone before the next interaction.
- **Controlled inputs drop fast keystrokes.** A character typed while React commits the previous one is lost: `type("15")` can yield `"1"`. `fill()` the whole value, or press one key at a time with an assertion between.

## Diagnosing a failure: find the mechanism, never re-roll

1. **Get a repro rate.** `pnpm e2e:ci <spec> --repeat-each=10`. "3 failures in 10" is a mechanism to find; "it failed once" is not anything yet. After the fix the same command, at 0 in N, is the proof.
2. **Rule out a starved machine.** Compare the failing run's per-test durations with a green one. Everything 3x slower is infrastructure; padding timeouts for it only hides the next real bug.
3. **Read the trace, not just the error.** `pnpm exec playwright show-trace <trace.zip>`: the DOM snapshots and the network log answer what the message cannot (two dialogs and one overlay; a request that never went).
4. **"Element not found"? Suspect the request.** A mutation refused by client validation and one that answered 500 both look like a missing element later. Find the request in the trace, or its absence.
5. **Instrument when the cause is invisible.** Patch the suspect DOM method in `page.evaluate` and log `new Error().stack` (a focus thief shows up this way). Remove the probes before committing.
6. **Prove the fix is falsifiable.** Revert it and watch the test go red under the same repro command, then restore. A test that passes with and without the fix documents nothing.

When a test fails in one environment only, suspect the environment first: the Postgres version, the libc's collation, a missing variable.

## Before pushing a change here

`pnpm typecheck` covers this tree, and CI runs `playwright test --list` (`PLAYWRIGHT_SKIP_SERVER=true`), which catches a method added to the wrong page object. Run the changed specs with `pnpm e2e:ci <spec>`, which uses a fresh database and a production build like CI.
